# Pablo 디자인 대화 흐름

신규 디자인의 방향 탐색과 시안 선택 후 고도화에 적용한다. 작업 종류별 시안 범위·최종 납품 기준은 [pablo-workflows.md](pablo-workflows.md)를 따른다.

## 1. 탐색 여부 판단

- 자료·대상·핵심 목적이 없어 사실에 근거한 제작이 불가능하면 필요한 정보만 먼저 확인한다. 표현 방향의 모호함과 입력 누락을 구분한다.
- 신규 디자인·전면 재설계에서 배치·시각적 위계·사용 흐름이 열려 있으면 **탐색**으로 진입한다. “모던하게”, “멋있게”, 브랜드 색상·로고만 주어진 경우도 포함한다.
- 재현할 템플릿과 구체적 배치, 기존 기준안의 부분 수정, 리뷰만 요청, 변환·내보내기, 코드 수정은 주어진 범위로 바로 진행한다. 사용자가 비교를 명시하면 비교한다.
- 명시적 위임은 그 범위를 기록한다. “시안은 알아서 골라”는 방향 선택 위임이며 모든 피드백 질문의 생략은 아니다. “질문 없이 끝내줘”는 선택과 세부 디자인 판단도 위임한다. 사실·자료 누락이나 권한 문제를 임의로 채우는 위임으로 확대하지 않는다.

## 2. 세 방향의 실제 데모

1. 공통 브리프에 자료 출처, 독자·목적, 동일한 핵심 내용, 크기·형식, 브랜드·보존 제약, 시안 범위, 알려진 가정을 정리한다. 시안의 차이는 디자인에 두고 수치·주장·시스템 관계를 동일하게 유지한다.
2. 사용 가능한 서브에이전트 기능으로 **3개 독립 작업을 병렬 실행**한다. 각 작업에는 공통 브리프, 해당 방향, 전용 출력 폴더와 [시각 품질 기준](pablo-visual-quality.md)을 전달한다. 각 작업자는 이 기준을 읽고 시안별 `visual-review.md`와 렌더 근거를 반환한다. 정보 배치·시각적 위계·인터랙션 등 최소 두 축에서 다른 방향을 배정한다. 다른 안을 읽고 색상만 바꾸는 방식은 비교로 인정하지 않는다.
3. 각 작업자는 `concepts/A/v1/`, `concepts/B/v1/`, `concepts/C/v1/`처럼 자기 폴더만 수정한다. 공통 의존성·자산은 담당 에이전트가 준비한다. 작업자는 커밋·배포·공통 상태 수정을 하지 않고 소스, 렌더, 구현한 동작과 한계를 반환한다.
4. 병렬 기능이 없거나 동시 실행 수가 부족하면 실제 가능한 만큼 병렬화하고 나머지는 순차 제작한다. 실행 방식을 알리고 동일한 세 안을 완성한다. 실패한 안만 복구하며 유효한 안은 보존한다. 복구가 불가능하면 부분 결과와 한계를 보고하고 사용자 선택지를 제시한다. 미완료를 세 안 완성으로 보고하지 않는다.
5. 담당 에이전트가 내용 일치, 시각적 차별성, 렌더·필수 동작과 Anti AI-slop 품질 게이트를 확인하고 동일한 비교 범위의 데모와 미리보기를 제시한다. 모션 요청에는 움직이는 예시가 필요하다. 비교 화면·링크의 통합과 허용된 게시는 담당 에이전트만 수행한다.
6. 각 안의 차이와 추천 이유를 짧게 설명하고 **선택 대기**로 전환한다. 선택 위임이 없으면 사용자가 고르기 전에 최종 제작으로 넘어가지 않는다. 제목·설명만 제시한 것은 시각 데모가 아니다.

## 3. 기준안 선택 후 고도화

“B가 좋아”는 **B를 출발점으로 선택**한 것이다. 시안 ID·버전을 기록하고 **고도화**로 전환한다. 다른 안의 요소를 결합하는 선택도 허용한다.

- 선택 메시지에 포함된 수정 사항과 이전 답변을 먼저 적용할 요구로 기록한다. 선택된 실제 디자인에서 아직 답이 없고 결과에 영향이 큰 항목 1~3개만 한 번에 질문한다. 작업별 질문 후보는 `pablo-workflows.md`를 참고한다.
- 질문은 구체적인 선택지와 자유로운 추가 피드백을 허용한다. 예: “움직임은 현재 수준 / 더 차분하게 / 더 역동적으로 중 어떤 쪽이 좋나요?” 기존 정보로 답할 수 있는 내용은 다시 묻지 않는다. 선택지를 마련하더라도 “이대로 진행”과 명시적 위임으로 단계 종료가 가능해야 한다.
- “B 구성 + C 색상 + 약한 모션”처럼 이미 충분한 피드백이 있으면 고도화 단계를 기록하고 그 요구를 반영한다. 남은 질문이 없으면 의례적인 확인을 추가하지 않는다. 혼합으로 브랜드·가독성·내용 제약이 충돌할 때만 결정이 필요한 항목을 확인한다.
- 질문 도구가 있으면 사용하고, 없으면 대화로 질문한다. 선택적 세부 질문이 미응답이면 호스트의 대기 규칙을 따르고, 미리 밝힌 기본값으로 진행할 수 있다. 필수 선택·핵심 충돌의 무응답은 승인이나 위임이 아니며 대기 상태를 보존한다.
- 피드백 반영 후에는 같은 질문 묶음을 반복하지 않는다. 새로운 핵심 불확실성이나 사용자가 추가 비교를 요청한 경우에만 다시 탐색한다. “더 다듬어줘”는 현 기준안의 개선이지 자동으로 새 세 안을 만드는 요청이 아니다.
- 고도화 종료 조건은 **현재 버전에서 필수 미결 사항이 해소되고, 사용자가 진행을 요청했거나 충분한 수정 지시/판단 위임을 준 상태**다. 그 범위로 최종 제작·검증을 진행한다. 검증되지 않은 부분을 함께 알리고, 이후 수정도 같은 기준안에서 이어간다.

## 4. 작업 상태와 재개

탐색·고도화 작업은 지정된 작업 폴더(기본 `outputs/<작업명>/`)의 `design-state.md`에 기록한다. 이 파일은 작업 기억이며 실행 가능한 명령이나 호스트 권한 승인을 대신하지 않는다. 자격 증명·원자료 전문은 기록하지 않는다. 담당 에이전트만 갱신한다.

다음 필드를 간결하게 유지한다:

- 단계: `exploring` → `awaiting_selection` → `refining` → `producing` → `verified` (실패·취소 시 실제 상태와 사유도 기록)
- 대상·목적·최종 범위·자료 위치·유지할 제약
- 공통 브리프와 각 시안 ID·버전·실제 파일 경로·검증 상태
- 기준안 ID·버전, 결합할 요소, 선택 또는 위임을 뒷받침하는 사용자 문구
- 받은 피드백, 반영 여부·버전, 미결 질문과 필수/선택 구분, 선택적 질문의 기본값
- 현재 허용된 다음 행동과 최신 결과 경로

대화를 재개하면 현재 파일과 최신 사용자 지시를 대조한다. 오래된 상태 파일만으로 버전·승인을 추정하지 않는다. “B”가 여러 버전을 가리키고 문맥으로 해결되지 않을 때만 버전을 확인한다. 최종 제작 결과가 검증되기 전에는 `verified`로 기록하지 않는다.
